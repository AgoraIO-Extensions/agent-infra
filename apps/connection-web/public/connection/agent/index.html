C Connection 使用指南 登录控制台

Connection MCP · 开发者接入指南

将 Connection 接入自建 Agent

先由 Connection 管理员注册客户端，再由开发者实现回调、配置服务凭据、引导用户确认授权、在服务端取得独立访问令牌，再通过一个 MCP 入口调用外部服务。RehoboamAI 使用的授权确认与回跳流程，就是下面的 Agent PAT Binding。

1. 选择鉴权方式

  • 产品内提供“连接 Connection”按钮：使用 Agent PAT Binding。管理员注册你的 Consumer，用户逐一确认，令牌直接交付你的服务端。以下第 2–4 步详细说明。
  • 已有 remote OAuth MCP 客户端：使用 Authorization Code + PKCE，由客户端 SDK 处理浏览器登录、回调和令牌生命周期。见第 5 步。
  • 个人脚本或手工配置的客户端：用户在访问令牌页签发 Connection PAT，保存到服务端 Secret。通用 PAT 使用 Portable PAT Consumer。

三种方式都访问 __CONNECTION_ORIGIN__/mcp，传输协议为 Streamable HTTP。令牌认证只证明“是谁、哪个客户端”；外部账号连接和 Action 授权还需分别完成；只有管理员开启审批的连接器要求公司审批，现有及新增连接器默认关闭审批。

启用公司入口保护时，用户在浏览器先完成公司 OAuth 登录，回跳后自动完成入口校验（未自动跳转时等待两秒，使用出现的“完成公司登录”按钮），再按 LDAP 账号登录 Connection；两次账号可以不同，业务身份和已有授权仍归 LDAP 账号。MCP、metadata、DCR、token 与 PAT Binding 后端创建/领取请求不需要 公司入口 Cookie 或额外 apiKey。用户确认页仍需入口准入和 Connection 登录。

公司登录、LDAP 授权登录和授权确认均保留用途独立的短期防伪校验。会话丢失或页面失效时，按页面提示重新打开授权入口并核对账号，不会自动重放提交。若企业微信等内置浏览器隔离或清除 Cookie，请复制页面中的恢复入口到系统浏览器继续。URL 仅携带不透明流程标识，不携带密码、PAT 或防伪证明；不要自行拼接参数。外部系统回调仍按各 Provider 的 state/PKCE 校验，客户端后端的创建/领取契约不变。

入口会话过期时，用户重新打开控制台完成入口登录后主动重试，不自动重放提交；退出 Connection 不等于退出公司 SSO。

2. 管理员注册 Agent，开发者取得服务凭据

开发者或普通用户：请把 Consumer ID、Agent 名称和固定 Callback URL 提交给 Connection 管理员，由管理员添加 Agent。该管理页面仅对管理员开放；普通用户直接访问会返回“我的 Connection”。

Connection 管理员：打开Agent 接入管理页（仅管理员），填写以下信息并点击“注册 Agent”。

  • Consumer ID：稳定标识，例如 my-agent，3–80 位小写字母、数字或连字符，首位为字母或数字。
  • Agent 名称：用户授权页展示的名称，1–100 个字符，例如 My Agent。
  • Callback URL：你的服务端固定 HTTPS 回调地址，例如 https://agent.example/connection/callback。不能包含用户名、密码或 fragment；绑定请求不能临时替换 callback。注册时只校验地址格式，不会访问或检查该接口是否已存在；开始用户绑定前，开发者须实现该回调并确保用户浏览器可访问。

不要用个人 PAT 代替 Agent 服务凭据。注册后页面仅展示一次服务凭据，请管理员安全交付给开发者并保存到后端 Secret。它用于创建绑定和领取 PAT，不能用于调用 MCP，也不能交给浏览器或模型。注册后直接进入能力配置，请选择 Provider 与 Action 并点击“保存能力配置”；之后可通过“配置能力”查看和修改已保存的选项。它是用户可申请的能力上限，不会直接授予账号权限。用户看到“该客户端尚未配置所需能力”时，请联系 Connection 管理员申请开通。

3. 实现“连接 Connection”与授权回跳

发起绑定：用户在你的产品登录后，后端用服务凭据发送以下请求，并保存绑定与原发起用户、会话及实例的关联。principalHint 可省略；省略时由用户确认关联当前 Connection 账号，不要求两边账号属于同一人。如业务需要校验邮箱一致，可从可信登录态取得公司邮箱作为 principalHint；提供时必须匹配 Connection 账号邮箱（去除首尾空格并转小写），不能传空白、null 或非法类型。

POST __CONNECTION_ORIGIN__/api/v1/connection/pat-bindings
Authorization: Bearer <Agent 服务凭据>
Content-Type: application/json
Idempotency-Key: <本次创建操作的 UUID>

{
  "consumerId": "my-agent",
  "name": "my-agent-default"
}

成功返回 HTTP 201，包含 bindingId、authorizationUrl 和 expiresAt。后端保存 bindingId → 当前产品用户/会话/实例 的关联，再让用户在新 tab 打开返回的 authorizationUrl。不要自行拼授权 URL，也不要把浏览器提交的用户 ID 当作身份权威。

用户确认：用户在 Connection 登录后会看到“授权 My Agent”页面，展示当前 Connection 账号、客户端名称、令牌名称、链接有效期及将交付客户端后端的账号信息。点击“确认并返回 My Agent”后，Connection 创建该用户、该 Consumer 的独立实例与 PAT，并以 HTTP 303 回到已注册地址：

授权确认表单自动携带绑定当前登录会话、账号和本次请求的校验码，最多五分钟有效且不超过绑定链接期限。企业微信等内置浏览器缺失或发送 null 来源时，仍需校验码与登录验证全部通过；明确跨域来源拒绝。无需客户端修改创建/领取接口，不要代提交确认表单或把校验码、PAT 放到 URL。旧页面、校验码过期或账号切换时，重新打开授权页；排查只需提供错误编号。企业微信实际兼容性需用真实客户端验收。

https://agent.example/connection/callback?binding_id=<bindingId>

服务端领取：回调必须验证 binding_id 属于原来发起绑定的用户、会话和实例；不要接受任意 ID 后给当前用户绑定。后端使用同一 Consumer 的服务凭据领取：

POST __CONNECTION_ORIGIN__/api/v1/connection/pat-bindings/<bindingId>/claim
Authorization: Bearer <Agent 服务凭据>
Content-Type: application/json
Idempotency-Key: <本次领取操作的另一个 UUID>

{"consumerId": "my-agent"}

成功响应的 issued 对象保留 consumerId、expiresAt、name、token 和 tokenId，并增加 account：id 是该 PAT 对应的稳定 Connection 用户标识，email 是当前邮箱（可能为 null），displayName 是显示名。将 Token 加密保存在原发起产品用户和实例的后端 Secret，逐用户隔离；页面可显示关联账号邮箱及显示名，但不得展示 Token。邮箱不能作为稳定身份键或两边同人的证明。旧客户端可继续传提示并使用原返回字段，无需重新绑定。

绑定链接当前有效期为 10 分钟，确认与领取都必须在返回的有效期内完成；PAT 的有效期以 issued.expiresAt 为准。领取只能成功一次，回调 URL 不携带 PAT。创建和领取使用不同的 Idempotency-Key；同一操作保持原 key 和参数，但不能依赖重放重新取回一次性 Secret。过期、已领取或响应丢失时，不循环领取或换 key 猜测重试，向用户说明并重新发起绑定；已签发的旧令牌可在访问令牌页撤销。

4. 用户连接账号，并授权给你的 Agent

“确认并返回”只完成客户端令牌绑定；令牌可使用同一用户已授权给该 Consumer 的多个 Provider，不会自动取得其他账号或 Action。请引导用户打开连接账号页，按以下顺序操作：

  1. 选择所需 Provider。连接器默认关闭公司审批，可直接连接自己的外部账号；仅管理员开启审批的连接器，先点击“申请连接”，填写用途、选择能力并确认免责声明，提交公司审批。
  2. 在我的 Connection中选择 Provider，查看连接或申请状态；开启审批时，指定审批人在待我审批页处理申请。用户不能自行批准，也不能靠签发 PAT 绕过已开启的审批。
  3. 审批关闭时直接连接；审批开启时获批后再连接。回到“连接账号”，选择已有账号或完成外部账号连接；开启审批的服务需要重新申请、续期或新版能力审批时，也从该账号的操作入口发起。
  4. 选择该账号，点击“授权客户端”，选择你的 Agent，核对所需 Action 并确认。外部账号连接和 Consumer 授权是独立步骤；只有开启审批的连接器还需有效公司审批资格。审批关闭也不自动增加 Action 授权。

管理员开启审批后，无有效资格的已有直连账号也无法发起新调用；关闭审批不自动恢复已暂停或撤销的客户端授权。共享账号使用资格另行管理。

如果你的 Agent 或 Action 不在选择列表中，请联系管理员检查 Agent 注册、启用状态与 Declaration；不要换成其他 Consumer 的令牌。用户可分别撤销客户端授权、撤销 PAT 或断开外部账号，影响范围不同。

5. 配置 MCP 鉴权并调用 Action

Agent PAT Binding 领取的 PAT 与手工签发的 Connection PAT 都由后端 MCP transport 设置为 Bearer header。以下是协议参数，SDK 配置字段以你实际使用的版本为准：

Transport: Streamable HTTP
URL: __CONNECTION_ORIGIN__/mcp
Authorization: Bearer <当前用户与实例的 Connection PAT>

支持 remote OAuth 的客户端可从 /.well-known/oauth-protected-resource/mcp 和 /.well-known/oauth-authorization-server 发现授权配置，通过 Authorization Code + PKCE 登录，按 SDK 要求处理 state、redirect URI、resource 和 token refresh。OAuth client 注册须与管理员确认；不要假设任意 SDK 都可动态注册。OAuth 登录流程与上述 PAT Binding 的 callback/claim 接口不同。

完成 MCP 初始化，再通过 tools/list 获取五个通用工具，按顺序使用：

  1. list_apps：发现 Provider。
  2. list_connections：查看当前主体可用账号。
  3. search_actions：查找所需操作；已知 Provider 时传入实际 schema 支持的 service，便于取得缺少连接或授权的引导。
  4. get_action_guide：读取输入 Schema、权限与幂等要求。
  5. execute_action：按真实工具 Schema 和 Guide 执行；不猜 Action ID，不传 Provider 凭证或自报用户、Agent、Consumer 身份。

服务凭据与用户 PAT 必须分开保存。令牌不得进入聊天、模型输入、前端存储、源码、日志或 URL；不要让不同用户共享一个 PAT。针对实际 SDK 和版本验证初始化、鉴权、发现与错误路径，Codex 的兼容性验证不代表你的 SDK 已兼容。

分析 GitHub Actions 失败时，先发现并确认用户已授权 github.get_workflow_job_logs。用 Job 列表取得 ID，读取日志后按 nextStartLine 继续；scanLimitReached 且没有下一页时请引导查看 GitHub 原日志。不要据此重跑构建。原始日志会进入已授权 Agent 或模型上下文，详细限制见GitHub 接入帮助。

6. 无权限时，如何引导用户恢复

连接器新增能力不会自动授予客户端；请在管理能力中选择并确认。候选列表由当前目录、客户端配置和公司审批范围决定，不按外部 scope 快照过滤。确认表示允许客户端使用，实际操作权限由外部系统判断；权限不足只影响本次操作，不取消已确认能力，外部权限恢复无需重复客户端确认。正常账号不显示“更新账号权限”按钮；只有系统判定需要处理时才显示升级或重连操作。兼容升级复用已有凭据，真正的凭据失效或需要 OAuth 时按提示更新凭据。账号或能力语义变化仍须重新处理授权；审批开启和共享账号遵循各自流程。不要让用户把凭据发到聊天中。

客户端需要把返回的引导展示成用户可点击的提示。当前带 service 的 list_connections / search_actions 空结果可在 result.structuredContent.guidance 中返回 message、messageKey、reasonCode、retryable 与 nextAction。OPEN_CONNECTION_WEB 的 URL 会指向具体 Provider 的连接页：

{
  "reasonCode": "PROVIDER_AUTHORIZATION_REQUIRED",
  "retryable": false,
  "nextAction": {
    "type": "OPEN_CONNECTION_WEB",
    "url": "__CONNECTION_ORIGIN__/connection/connections?provider=jira&intent=authorize"
  }
}
  • PROVIDER_NOT_CONNECTED：提示用户前往连接账号，按页面当前设置连接账号；仅开启审批的连接器需先申请并获批。
  • PROVIDER_AUTHORIZATION_REQUIRED：提示在“连接账号”中选择账号，再“授权客户端”；仅当连接器开启审批且缺少公司资格时，先提交申请，并到连接申请选择对应 Provider 查看进度。
  • PROVIDER_REAUTHORIZATION_REQUIRED：提示在“连接账号”查看当前账号状态，根据页面提示重新连接或重新确认客户端授权；连接器开启审批时，还需检查并恢复公司资格。
  • PROVIDER_UNSUPPORTED / CONTACT_ADMIN：联系 Connection 管理员申请接入该 Provider；不能把它解释为用户尚未授权。
  • SEARCH_NO_RESULTS / REFINE_SEARCH：改用更简短的查询；空搜索结果不一定是权限问题。
  • HTTP 401 或令牌失效：重新完成客户端登录或 PAT Binding；手工 PAT 用户前往访问令牌页检查有效期与撤销状态。

当前覆盖范围：发现引导尚不细分所有公司审批状态；执行错误也不保证都有 nextAction.url，不能只处理这一字段。对于通用 FORBIDDEN 或没有链接的权限错误，显示服务端安全文案，并提供“我的 Connection”（连接与申请）和“使用指南”入口，让用户检查账号、审批及客户端授权；不要断言某项申请已获批或自动发起申请。

只有通过校验的 Connection 网站 URL 才可展示为操作链接，使用新 tab 打开，保留当前 Agent 会话。retryable: false 时等待用户处理，不自动重复执行；写操作结果未知时不要因授权恢复而重放原业务操作。

平台级 Delegated 接入

以上逐用户 PAT Binding 仍属于 Direct MCP。需要以注册 workload 代表当前 Principal 调用的 Agent 平台，应与 Connection 管理员对接 HTTP/OpenAPI Delegated 契约、workload 身份和短期委托上下文；Agent Platform 还需绑定稳定 Agent Actor。不能用自报身份或共享 PAT 替代该契约，也不能从 MCP URL 推测 Delegated 接口。

遇到 429 请按 Retry-After 等待后重试，不要循环提交。完整管理 API 文档需 Connection 登录；MCP 发现仍使用公开 metadata，不要求公司入口 Cookie。
